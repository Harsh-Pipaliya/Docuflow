DOCUFLOW | SOLO PRESENTATION
Read the paragraphs aloud. The time ranges are rehearsal cues.

Slide 1 | DocuFlow | 0:00–0:20
Suppose I upload a workshop agenda and the screen says “upload complete.” How do I know the PDF actually opens? That’s the question we built DocuFlow to answer. I can follow one file from upload to its final result and see why it passed or failed.

Slide 2 | Receiving the PDF | 0:20–0:43
Let’s follow that agenda. After I sign in and select it, our Flask API checks the filename, the declared file type, and the size. It rejects empty files and anything over ten mebibytes. If the agenda passes those checks, it gets a unique file ID and goes into private storage.

Slide 3 | From storage to the worker | 0:43–1:06
Once the upload finishes, Eventarc sends the worker a message identifying the exact version of the file to read. Processing can now continue in the background. For our demo, Floci runs the Google Cloud services locally, and Docker Compose hosts the worker that would normally run on Cloud Run.

Slide 4 | Inside the PDF | 1:06–1:31
The worker opens the file in an isolated process and checks its structure and pages. If the agenda is damaged or encrypted, the dashboard shows a failure reason. If it’s valid, the worker records its page count and calculates a fingerprint from its contents. Firestore keeps the history, and Cloud Logging records the outcome.

Slide 5 | What the tests proved | 1:31–2:00
That fingerprint explains one of our test results. When we renamed the agenda and uploaded it again, it got a new file ID, but DocuFlow recognized the identical contents. Replaying the original event left its history unchanged. Across fourteen samples, seven processed successfully, four failed validation, and three were rejected at upload. All twenty-five workflow checks passed.
